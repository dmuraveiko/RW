RW с точки зрения пользователя

0. Внешняя система передает нам идентификатор сервиса балансов, в ответ мы генерируем и отдаем внешней системе строку инвайта

-----------------------------------------------------------------------------------------------------------------------------------------

1. Для начала сеанса с ботом пользователь переходит по ссылке с инвайтом вида https://t.me/botname?start=invite
   (запасной вариант, если пользователь начинает сеанс с ботом без инвайта, то бот запрашивает инвайт в диалоге с пользователем)

2. Наша система единожды привязывает сессию пользователя Телеграма по инвайту к идентификатору сервиса балансов
   Может быть привязано несколько разных сессий пользователя Телеграма к одному идентификатору сервиса балансов

3. Требуется активация сессии. Для неактивированной сессии доступен только функционал необходимый для проведения активации

4. Процедура активации состоит в получении на наш кошелек USDT с кошелька пользователя небольшой суммы
   После чего мы запоминаем кошелек-отправитель в нашей системе

5. Если привязка кошелька-отправителя уже была ранее выполнена, то активация сессии требует использования того же самого кошелька-отправителя, что и при самой первой активации

-----------------------------------------------------------------------------------------------------------------------------------------

6. После активации становится доступен следующий функционал:

   а) Отображение сессий Телеграма, привязанных к идентификатору сервиса балансов
   б) Удаление этих сессий
   в) Установка/изменение кошелька-получателя USDT
   г) Запрет/разрешение выполнения получения USDT на кошелек-получатель
   д) Пополнение баланса пользователя
   е) Делегирование/прекращение делегирования функционала пополнения баланс пользователя (пункт в) другим аккаунтам Телеграма

Задача #1:

Подсистема бота Телеграма.

Реализовать бота Телеграма. То есть сервис, взаимодействующий с нашей системой и с API Телеграма

Должен уметь взаимодействовать с API Телеграма как напрямую по http, так и через наш сервис natsproxy
Для взаимодействия с нашей системой использовать NATS (без JetStream) с помощью асинхронных вызовов NATS Publish/Subscribe (не с помощью синхронных Request/Reply)

Реализовать первичную активацию и повторную активацию пользователя
Отображение привязанных сессии и их удаление

Не делать в рамках этой задачи (но предусмотреть на дальнейшую реализацию):
Делегирование/отмену полномочий, пополнение баланса и работу с кошельком-получателем

Сервис конфигурируется через переменные среды окружения токеном для работы с Телеграм, параметрами для подключения к natsproxy и к nats для взаимодействия с нашей системой, подключение к БД
А также ключами ed25519, которые следует использовать для подписания сообщений, отправляемых в NATS для прочих частей нашей системы, и проверки сообщений, получаемых из NATS от прочих частей нашей системы

Сервис использует свою собственную БД PostgreSQL

Через API к другим компонентам нашей системы (API реализовано через NATS) реализуется следующее:

1) Принимает через NATS запрос на генерацию инвайтов, генерирует, сохраняет в своей БД, отдает сгенерированный инвайт через NATS

2) Функционал для пополнения/проверки пополнения небольшой суммы:
   Кошелек-отправить узнается от пользователя
   Сумма генерируется ботом
   Для начала пополнения-проверки кошелек-отправитель, сумма отправляется через NATS; получает через NATS информацию о кошелке-получателе и об окне времени, в течении которого можно выполнить пополнение; возможен ответ о том, что операцию нужно провести позднее, но не прямо сейчас
   Уведомление об успешности завершения пополнения получается через NATS

3) После получения уведомления отмечает сессию как активную (идентификатор транзакции USDT, которая использовалась для подтверждения, так же сохраняется)

4) Список привязанных сессий запрашивается через NATS, удаление привязанных сессий реализуется через NATS

5) Функционал уведомления о нештатных ситуациях (сбов в БД, невозможность установки связи с Телеграм и т.п.) - информация отправляется в сервис сбора статистики RealWallet

P.S.:

Неактивированные сессии и активированные сессии должны сохраняться в разных таблицах БД, так как возможны многочисленные "мусорные" попытки активации сессий, не нужно захламлять таблицу активных сессий этим "мусором"

Задача #2:

Подсистема активных сессий.

Конфигурируется через переменные среды окружения: параметры подключения к БД, к NATS, собственный ключ ed25519 для подписи отправляемых сообщений, ключи для проверки получаемых сообщений
Взаимодействует с внешним миром через NATS

Использует БД PostgreSQL

Хранит соответствие активированной сессии бота Телеграма (в будущем возможно и сессия для веба и т.п.) и идентификатору баланса пользователя
Хранит кошелек-отправитель, используемый для первичной регистрации и для восстановления доступа

Будет хранить информацию о кошельке-получателе и о делегированных полномочиях (на данном этапе не реализовывать, но предусмотреть)

Получается от бота из задачи #2 информацию об успешной активации сессии
Перепроверяет эту информацию из подсистемы пополнения кошелька
