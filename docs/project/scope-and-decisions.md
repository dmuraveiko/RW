| Первичная и повторная активация через небольшое пополнение USDT | REQ | `raw/rw_cab0.txt:13-18`, `raw/rw_cab0.txt:57-63` |
| Запоминание первоначального sender wallet | REQ | `raw/rw_cab0.txt:15-18`, `raw/rw_cab0.txt:84-85` |

## Что не реализуем

| Область | Как учитываем |
| --- | --- |
| Подсистема пополнения из `rw_topup.txt` | Только NATS-контракт, клиентский адаптер, fake и contract tests |
| Подсистема blockchain-статусов из `rw_status.txt` | Не вызываем напрямую; это внутренняя зависимость команды top-up |
| Делегирование полномочий | Extension seam в доменной модели, без таблиц/handlers/UI текущего релиза |
| Пополнение пользовательского баланса | Не реализуем; activation payment — отдельный сценарий подтверждения |
| Работа с receiver wallet после активации | Не реализуем |
| Сам сервис natsproxy | Только транспортный адаптер по согласованному контракту |
| Сервис диагностики | Только публикация событий и локальный sink для разработки |

## Утверждённые решения

| ID | Решение | Статус | Почему |
| --- | --- | --- | --- |
| ADR-001 | Один monorepo, два бинарника: `rw-bot`, `rw-active-sessions` | ПРИНЯТО | Два разных владельца данных и независимое масштабирование |
| ADR-002 | Две независимые PostgreSQL БД; межсервисных SQL join нет | ПРИНЯТО | Требование собственной БД бота и слабая связанность |
| ADR-003 | Active-sessions — источник истины; бот хранит read projection | ПРИНЯТО | Исключает два равноправных источника активного статуса |
| ADR-004 | Transactional outbox/inbox поверх Core NATS | ПРИНЯТО | Core NATS не хранит сообщения для отключённого подписчика |
| ADR-005 | Публичные схемы — JSON Schema; payload подписывается как неизменяемые bytes | ПРИНЯТО | Межъязыковая интеграция без неоднозначной canonical JSON подписи |
| ADR-006 | Локально direct long polling; production direct webhook; natsproxy — третий runtime mode | ПРИНЯТО | Удобный локальный запуск и горизонтальное масштабирование production |
| ADR-007 | Удаление сессии — soft revoke с аудитом | ПРИНЯТО | Безопасность, расследование и идемпотентность |
| ADR-008 | Invite содержит 32 random bytes в base64url, хранится только SHA-256 digest | ПРИНЯТО | Высокая энтропия, отсутствие секрета в БД, укладывается в Telegram limit |
| ADR-009 | Wallet и balance ID внутри системы остаются opaque strings до network-specific validation | ПРИНЯТО | Исключает ошибочную нормализацию адресов другой сети |

## Детализация решений

Точные версии, TTL, retry, retention, wallet/network policy, Telegram identity, self-revoke, key formats и эксплуатационные параметры утверждены в [технических решениях](technical-decisions.md). Внешние команды реализуют versioned contracts из [contracts.md](contracts.md); несовместимость решается adapter или новой major version, а не скрытым ослаблением нашей модели.

## Словарь

| Термин | Значение в проекте |
| --- | --- |
| Balance ID | Непрозрачный идентификатор пользователя во внешнем сервисе балансов |
| Telegram identity | Пара `(bot_id, telegram_user_id)`; `chat_id` используется только для доставки |
| Session ID | UUIDv7 конкретной binding; после revoke новый invite создаёт новую session |
| Inactive session | Привязанная по invite, но ещё не подтверждённая сессия |
| Active session | Сессия, которую active-sessions подтвердил после повторной проверки top-up |
| Activation attempt | Один ограниченный по времени процесс доказательства контроля sender wallet |
| Sender wallet | Кошелёк пользователя, с которого выполнен подтверждающий перевод |
| Projection | Локальная неавторитетная копия состояния другого сервиса для UI/маршрутизации |
| Revoke | Логическое отключение сессии без уничтожения аудита |
